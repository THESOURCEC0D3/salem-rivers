# 1. PROJECT OVERVIEW

## 1.1 What this website is

A **marketing / invitation website for a single-location Nigerian Pentecostal church** — *Salem Rivers*, at 1 Faith Avenue, Rumuomasi, Port Harcourt, Rivers State, Nigeria.

Two naming observations the incoming team must resolve:

- The codebase calls the church **"Salem Rivers"**, flagged `[CONFIRM]` in the content file. Client-supplied event flyer artwork reads **"Foundation Faith Church, Salem City of Faith"**. These are unreconciled. "Salem Rivers" may be a working title.
- The lead figure is **Bishop Hilary Ogoliegbune** (spelling confirmed from flyer artwork). The same flyer describes him as "National Coordinating Bishop" and names **Archbishop Dr Sam Amaga** as "Salem Family Worldwide — Chief Host". This implies Salem Rivers is one branch of a larger denominational network. **That relationship is documented nowhere in the codebase and should be clarified before redesign.**

It is a **static brochure site**. No CMS, no database, no authentication, no API routes, no server actions, no form submission of any kind. Every route prerenders to static HTML at build time.

## 1.2 Primary purpose

Documented explicitly in `HANDOFF.md` §1, and the code is faithful to it:

> **"The entire site has one job: compel a first-time *physical* visit. The livestream is always a subordinate fallback, never a co-equal call to action."**

This produces two architectural laws governing every file:

### Law 1 — The Single Funnel

Almost every call to action points at `/visit`. Enforced by a single exported constant:

```ts
export const PLAN_VISIT_HREF = "/visit";   // app/content/church.ts:391
```

Imported by 8 separate components. **No section of any page is a dead end** (with the documented exception of the Glimpse strip).

### Law 2 — WhatsApp-First, No Forms

There is not one `<form>`, `<input>`, or `<textarea>` in the codebase. Every "contact us" affordance is a `wa.me` deep link with a context-specific pre-filled message, generated by one helper:

```ts
export function whatsappLink(message?: string): string   // app/content/church.ts:374
```

Stated rationale: an unsure visitor will not fill in a form, and WhatsApp is how people actually make contact in this market. **12 distinct WhatsApp links** exist, each pre-filled according to where it was clicked — e.g. *"I'd like to serve in the Choir department"*, *"I'd like to come to 2nd Quarter Thanksgiving"*, *"Hello Bishop, I'd like to ask a question"*.

## 1.3 Audience

| Priority | Audience | Evidence in code |
|---|---|---|
| **1 — Dominant** | Unchurched / new-to-area person considering a first visit | Entire funnel design; `/visit` is the keystone; About page exists to "remove objections"; anxiety-reducing copy throughout |
| **2** | Existing members | Events page, Get Involved serving teams, giving |
| **3** | Diaspora / remote viewers | `/watch` — deliberately deprioritised, currently a placeholder |

Technical context is stated explicitly in `HANDOFF.md` §5 and `MASTER.md`: **"mobile-first (cheap Android, patchy data) → optimize images, sub-3s"**. This Nigerian-market assumption justifies several architectural decisions — the YouTube facade pattern, aggressive image optimisation, no autoplay video, and the WhatsApp-first contact model.

## 1.4 Primary user goals

1. **"Is this church real, and is it for people like me?"** — trust, answered by photography, the Bishop's words, testimonies, and plain-language beliefs.
2. **"When and where do I go?"** — service times (7:00 AM Sunday, 5:30 PM Wednesday) in the hero above the fold, the footer, and `/visit`.
3. **"What will happen when I walk in?"** — anxiety reduction. *Substantial content authored for this is currently unrendered — see §5.2.*
4. **"Can I ask a question without committing?"** — persistent floating WhatsApp button on every page.
5. **"What's happening soon?"** — Events page and the homepage next-event card.
6. **"Where do I fit?"** — Get Involved, six serving departments.

## 1.5 Primary business (ministry) goals

1. **Convert web visitors into physical Sunday attendees** — the single measurable objective.
2. **Generate WhatsApp conversations** — the site's only lead-capture mechanism.
3. **Establish local search presence** — real local-SEO engineering: `Church` schema.org JSON-LD injected on every page (`app/layout.tsx:48-67`), plus deliberately consistent Name/Address/Phone across footer, `/visit`, and structured data.
4. **Recruit volunteers** into six departments.
5. **Enable online giving** — built but gated behind `church.give.enabled: false`.
6. **Provide livestream access** — acknowledged, deliberately deferred.

## 2.3 Critical site-map findings

**① `/contact` is a live 404 on every page.** `Footer.tsx:116` renders `<Link href="/contact">`. No `app/contact/page.tsx` exists. Verified: `/contact` → **404**; all six other routes → **200**. `HANDOFF.md` §6 states Contact is *"by design **not a page** — the footer carries canonical address/map/phone"*, so the footer link contradicts the documented decision.

**② `/visit` — the most important page — is absent from the primary navigation.** `navLinks` contains only Home, About, Events, Watch. This is deliberate (comments at `church.ts:379-382` say so): it is reached exclusively through high-contrast buttons. The strategic bet is that a *button* converts better than a *nav item*. Flagged here as an **intentional decision, not an oversight**.

**③ There is no `not-found.tsx`.** A 404 renders Next.js's unstyled default — no header, no footer, no route back into the site. `/contact` sends users there from every page.

**④ No `sitemap.xml`, no `robots.txt`.** Neither `app/sitemap.ts` nor `app/robots.ts` exists.

## 3.2 Existing member

Poorly served relative to newcomers — a deliberate trade-off, but worth naming.

```
ENTRY (direct, knows the site)
   ↓
Header nav → Events ─────→ /events
   │                        Upcoming (4) + Past (4)
   │                        → WhatsApp "I'd like to come to [event]"
   │
   ├→ Home → Get Involved → WhatsApp "I'd like to serve in [dept]"
   │
   ├→ Watch → "Coming soon"          ← DEAD END
   │
   └→ Give → "Coming soon"           ← DEAD END
```

**Gaps:** no member login, no small-group/unit finder, no sermon archive, no prayer-request channel, no newsletter, no giving. Three member-facing destinations are placeholders. Everything routes back to `Plan Your Visit`, which is meaningless to someone who already attends.

## 3.3 Someone wanting prayer

**This journey does not exist as a designed path.**

There is no prayer request page, no prayer form, no dedicated prayer CTA, and no prayer-specific WhatsApp deep link. "Prayer" appears only as *content* — in the hero tagline, the Bishop's statement, the beliefs cards, and department blurbs.

The only available route is incidental:

```
Any page → floating WhatsApp button
        → "Hello Salem Rivers! I have a question about visiting."
        → user must manually delete and retype their prayer request
```

The pre-filled message is actively wrong for this intent. For a Pentecostal church — where the beliefs section states *"We're a praying church… we expect Him to answer"* — this is the **single largest journey gap in the product**.

## 3.4 Someone wanting to donate

```
Home Hero → [Give online]  ← the ONLY entry point on the whole site
   ↓
/give → "Coming soon" + pulsing red dot
        "Soon you'll be able to give securely online."
   ↓
Only onward action: [Plan Your Visit]  ← redirects a donor to a visit
```

- The footer "Give" link is **feature-flagged off** (`church.give.enabled: false`), so the hero button is the sole discoverable entrance.
- The hero grants "Give online" **secondary-CTA prominence beside the primary conversion action** — the most prominent secondary button on the site leads to a dead-end placeholder.
- **No offline alternative** — no bank details, no account name, no "give in person on Sunday". A motivated donor currently cannot give at all.
- Intended implementation per `HANDOFF.md` §8c: Paystack or Flutterwave.

## 3.5 Someone wanting to watch sermons

```
Header → Watch  ──┐
ReadyToJoin ──────┤→ /watch → "Coming soon" + pulsing red dot
(all 3 pages)     ┘           "Our livestream is on the way"
                                   ↓
                        Only action: [Plan Your Visit]
```

- The **pulsing red dot** is the universal visual language for *"live now"*. Here it decorates the words "Coming soon" on a page with no stream. A returning viewer scanning for a live indicator will misread it.
- `church.watch.nextLiveLabel` says **"Live this Sunday from 7:00 AM"** and is rendered on the homepage inside `ReadyToJoin` — **promising a livestream that does not exist**.
- `church.watch.youtubeUrl` and `facebookUrl` both point to `example` placeholder accounts and are **not linked from the Watch page at all** — only from the footer social icons.
- A complete implementation design already exists in `HANDOFF.md` §8a: schedule-based live detection via `Intl.DateTimeFormat` pinned to `Africa/Lagos`, SSR-safe (render not-live, flip in `useEffect`), `YouTubeFacade` for the not-live state. **`YouTubeFacade` is already built and tested — parked, waiting on this page to be built.**

## SECTION 1 — HERO

**File:** `app/components/home/Hero.tsx`

**Purpose.** The "trailer". Prove the church is real, warm and currently active within ~5 seconds, and surface the two logistics facts a visitor needs before anything else.

**Visitor question answered.** *"Is this a real, living church — and when/where does it meet?"*

**Strengths**
- Genuinely full-bleed photograph of a packed service; conveys scale and life instantly.
- **Service times and location are above the fold at 375px** — satisfies the design system's hardest homepage rule.
- Sophisticated three-layer legibility system rather than a naive dark overlay.
- Solid `#100a17` base layer beneath the image so text never flashes unreadable during load.
- `priority` on the LCP image; `sizes="100vw"` accurate to layout.
- Deliberately breaks the site `Container` (`max-w-[110rem]` vs `max-w-6xl`) so copy hugs the left edge and more photograph reads — a considered, documented decision.

**Weaknesses**
- **`Give online` is the secondary CTA and leads to a placeholder page.** The most prominent secondary action on the homepage is a dead end.
- The hero tagline is a doctrinal statement (*"In Salem God is making many mighty through the Word and Prayer"*) rather than newcomer-facing orientation. The previous copy — *"Come as you are — there's a seat saved for you"* — addressed the target persona; the current line addresses the already-convinced. **Client decision; noted as strategic observation only.**
- `min-h-[calc(100svh-4rem)]` forces a full-viewport hero with **no scroll affordance** — no chevron, no peek of the next section.
- Alt text is generic; does not name the Bishop or the occasion.

**Components inside.** `next/image`, `next/link`, `ClockIcon`, `MapPinIcon`, `ArrowRightIcon`, `HeartIcon`. Notably does **not** use `Container`, `Section`, or `Button` — all hand-rolled.

**Animations.** Hover only: both CTAs `-translate-y-0.5` with `shadow-lg → xl`, 200ms `ease-out`. No entrance animation, no parallax, no autoplay. `backdrop-blur-sm` on info chips.

**CTAs.** ① `Plan Your Visit` → `/visit` (white pill, primary). ② `Give online` → `/give` (translucent, `HeartIcon`).

**Dependencies.** `church.name`, `church.tagline`, `church.serviceTimes`, `church.neighbourhood`, `church.city`, `church.give.href`, `PLAN_VISIT_HREF`, `/images/HeroImage3-clean.png`.

**Layering system (preserve in any redesign):**

| Layer | z-index | Purpose |
|---|---|---|
| Base fill `#100a17` | `-z-30` | Prevents unreadable flash during image load |
| `<Image fill object-cover>` | `-z-20` | The photograph |
| L→R scrim `from-black/90 via-black/60 to-black/25`, `md:via-black/45 md:to-transparent` | `-z-10` | Legibility under copy; **clears entirely from `md` up** so stage/choir/LED wall stay visible |
| Bottom vignette `from-black/40` | `-z-10` | Settles the lower edge |

## SECTION 2 — BISHOP'S WELCOME

**File:** `app/components/home/PastorWelcome.tsx`

**Purpose.** Put a face and a voice to the institution immediately after the hero. Leadership is the fastest trust proxy for a church.

**Visitor question answered.** *"Who leads this church, and what do they actually want for me?"*

**Strengths**
- Real photograph of the Bishop (`BishopHillary.png`), 4:5 portrait, left column with the quote right — the subject faces *into* the text, correct compositional practice.
- Mission statement set in the serif display face at `text-2xl/3xl` — treated as a pull-quote, appropriately reverent.
- Low-friction WhatsApp escape hatch with a role-appropriate pre-filled message.
- Correctly uses semantic `<blockquote>`.

**Weaknesses**
- **No `<Section>` heading structure.** The eyebrow "A word from our Bishop" is a `<p>`, so this section contributes **no `<h2>` to the document outline**. A screen-reader user navigating by heading jumps from the hero `<h1>` straight to "Real people, real Sundays".
- The statement is a vision/mission declaration, not a personal welcome — it says what the church does, not what a nervous first-timer can expect. (Client-supplied copy.)
- No bio, no tenure, no family detail — the trust-building specifics `leadership[].bio` reserves are still placeholder.
- Source image is a 1.9 MB PNG of a photograph (delivers as ~110 KB WebP, so a repo-weight rather than runtime issue).

**Components inside.** `Container`, `next/image`, `WhatsAppIcon`. Grid `lg:grid-cols-[0.8fr_1fr]`.

**Animations.** None beyond the WhatsApp link's `hover:underline`.

**CTAs.** WhatsApp → *"Hello Bishop, I'd like to ask a question about Salem Rivers."*

**Dependencies.** `church.pastor.{name,title,words}`, `church.name`, `whatsappLink()`, `/images/BishopHillary.png`.

## SECTION 3 — A GLIMPSE OF US

**Files:** `app/components/home/GlimpseStrip.tsx` · **Data:** `app/components/glimpseImages.ts`

**Purpose.** Social proof through photography. The design-system rule is explicit: **"Faces, not the building."**

**Visitor question answered.** *"What do the people here actually look like — and would I fit in?"*

**Strengths**
- **Five real photographs, no placeholders** — the most "finished" section on the site.
- Editorial mosaic: the first tile spans `col-span-2 row-span-2`, giving one hero tile plus four supporting tiles. At `lg:grid-cols-4` the five images fill the 4×2 grid **exactly**, no gaps.
- **Static imports** (not string paths) → build-time dimension detection, `placeholder="blur"` blur-up loading, and a *build error* rather than a broken image if a filename is wrong.
- Per-tile `sizes`: `100vw/50vw` for the featured tile, `50vw/25vw` for the rest.
- Genuine subject variety: worship, arrival/greeting, children, outreach, personal embrace.

**Weaknesses**
- **Purely decorative — zero CTA.** The only homepage section that is a conversion dead end. A visitor emotionally warmed by these photos has nowhere to go.
- No captions or context; photographs must carry all meaning alone.
- Several images carry the **"38th Anniversary / TOUGH LOVE / PRAISE NIGHT" event graphic burned into the artwork**, tying "everyday church life" to one specific past event — and they will visibly date.
- Heading "Real people, real Sundays" is generic.

**Components inside.** `Section`, `next/image`. `PhotoPlaceholder`/`PlaceholderNote` were removed once all five slots were filled.

**Animations.** Blur-up placeholder reveal on load. No hover state, no zoom, no lightbox.

**CTAs.** None.

**Dependencies.** `glimpseImages` → `worship1.jpg`, `Greeting1.jpg`, `children1.jpg`, `event1.jpg`, `Bishophug.jpg`.

> **Dead data:** `church.photos.glimpse` (the original four bracket labels) still exists in `church.ts` but is **no longer referenced by anything**.

## SECTION 4 — TESTIMONIES

**Files:** `app/components/home/TestimonySection.tsx` (wrapper) + `app/components/Testimonials.tsx` (carousel)

**Purpose.** Third-party validation. Peer voices answer objections the church cannot credibly answer about itself.

**Visitor question answered.** *"What happened to other people who walked in alone, like I would?"*

**Strengths**
- **The most accessible interactive component in the codebase.** Full ARIA carousel semantics: `aria-roledescription="carousel"`, per-slide `role="group"` + `aria-roledescription="slide"` + `aria-label="N of 4"`, `aria-hidden` on inactive slides, `aria-current` on dots, descriptive labels on every control.
- **Pauses on hover AND on focus** (`onFocusCapture`/`onBlurCapture`) — the focus case is commonly missed and correctly handled here.
- **Explicitly honours `prefers-reduced-motion` in JavaScript**: the auto-advance interval is never created for those users (`Testimonials.tsx:22`).
- Manual prev/next buttons plus clickable dots — never motion-only.
- Full-bleed background photograph with heavy `bg-black/75` overlay; cards borderless and transparent so the photo reads through.
- Deliberately built as a plain `<section>` + `Container` rather than `<Section>`, because `Section`'s heading colours are tuned for light backgrounds — a considered decision, documented in-file.

**Weaknesses**
- **Every testimonial is a placeholder**: names render as literal `[First name]`, contexts as `[Context]` / `First visited [last year]`. Anonymous testimonials read as fabricated and undercut the trust this section exists to build.
- **Auto-advance at 3.5 seconds is too fast** to finish reading a 2–3 line quote, and there is no progress indicator.
- The quote-mark badge uses `text-gold-soft` (`#f7ead0`) on `bg-white/15` — very low contrast, though decorative.
- The optional testifier photo still renders as a `photo-ph` gradient circle.
- `aria-hidden` hides inactive slides from assistive tech, but they remain in the **tab order** — a keyboard user can tab into an invisible slide's content.

**Components inside.** `Container`, `next/image` (background), `Testimonials` → `TestimonyCard`, `CarouselButton`, `QuoteIcon`, `ChevronRightIcon`.

**Animations.**

| Animation | Trigger | Duration | Detail |
|---|---|---|---|
| Slide transition | Auto every 3.5s, or manual | **500ms** `ease-out` | CSS `transform: translateX(-N*100%)` |
| Auto-advance | `setInterval` | 3500ms | Suppressed under reduced-motion |
| Dot expand | Becomes active | 200ms | `w-2.5 → w-6` |

# 6. NAVIGATION ARCHITECTURE

## 6.1 Desktop navigation (≥768px)

**File:** `app/components/Header.tsx` — a **Client Component** (`"use client"`), required for `usePathname()` and mobile menu state.

**Structure** — a single 64px-tall (`h-16`) flex row inside `Container`:

```
┌─────────────────────────────────────────────────────────────────┐
│ [◫] Salem Rivers      Home  About  Events  Watch   [Plan Your ▸] │
│  ↑ logo                    ↑ nav links            ↑ primary CTA │
└─────────────────────────────────────────────────────────────────┘
```

| Element | Implementation |
|---|---|
| **Logo** | `DoorMarkIcon` (custom doorway-plus-cross glyph) in a 36px `bg-primary` rounded square + church name in Fraunces. Links to `/`. `aria-label="Salem Rivers — home"`. |
| **Nav links** | Rendered from `navLinks` in `church.ts`. Pill hit areas (`rounded-full px-3.5 py-2`). |
| **Active state** | `pathname === link.href` → `text-primary` + `aria-current="page"`. |
| **Hover** | `hover:text-primary`, colour transition. |
| **CTA** | `<Button variant="primary" size="md">` → `/visit`, with `ArrowRightIcon`. |

## 6.2 Mobile navigation (<768px)

**Trigger.** A 44×44px (`h-11 w-11`) bordered square button, `MenuIcon` ⇄ `CloseIcon`.

**Panel.** Rendered *below* the sticky header bar, not as an overlay. Full-width rows (`px-4 py-3`) with a trailing `ArrowRightIcon` at 50% opacity, then a full-width `Plan Your Visit` button.

**Active state.** `bg-purple-soft text-primary` (note: the token is named `purple-soft` but now holds a blue value — see §8.1).

**Behaviours:**

```tsx
// Closes automatically on route change
useEffect(() => { setOpen(false); }, [pathname]);

// Locks background scroll while open, with cleanup
useEffect(() => {
  document.body.style.overflow = open ? "hidden" : "";
  return () => { document.body.style.overflow = ""; };
}, [open]);
```

**ARIA implemented:** `aria-expanded={open}`, `aria-controls="mobile-menu"`, dynamic `aria-label` ("Open menu" / "Close menu"), `aria-label="Primary mobile"` on the `<nav>`.

**Accessibility gaps:**
- **No focus trap** — Tab moves out of the open menu into page content behind it.
- **No Escape-key close** — the only way out is the toggle or a link.
- The panel is not a `role="dialog"`, so assistive tech does not announce it as a modal context.
- The scroll lock is applied but focus is not managed on open or close.

## 6.3 Dropdowns

**There are none.** The information architecture is deliberately flat — four top-level links, no sub-menus, no mega-menu, no hover-reveal panels. Appropriate for a six-page site, and it removes an entire class of mobile/keyboard accessibility problems.

## 6.4 Sticky behaviour

```
sticky top-0 z-40 border-b border-border/70 bg-background/85 backdrop-blur-md
```

- Sticks on all viewports.
- **Translucent** — `bg-background/85` plus `backdrop-blur-md` produces a frosted effect over scrolling content.
- `z-40`, sitting below the floating WhatsApp button (`z-50`) and the skip link (`z-[60]`).
- **No scroll-direction hiding, no shrink-on-scroll, no shadow-on-scroll** — the header is visually static apart from content passing beneath it.
- Every page that needs full-viewport height accounts for it explicitly: `min-h-[calc(100svh-4rem)]` (4rem = the 64px header).

## 6.5 Breadcrumbs

**None anywhere on the site.** Given a flat six-page architecture with no nesting, breadcrumbs would add no wayfinding value. The absence is appropriate, not an omission.

## 10.2 Reduced-motion handling

**This is handled better than in most production codebases — at two independent layers.**

**Layer 1 — global CSS** (`globals.css:92-104`):

```css
@media (prefers-reduced-motion: reduce) {
  html { scroll-behavior: auto; }
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

This neutralises *every* transition and animation on the site, including the infinite `animate-ping`.

**Layer 2 — JavaScript** (`Testimonials.tsx:22`):

```ts
if (window.matchMedia("(prefers-reduced-motion: reduce)").matches) return;
```

The carousel's auto-advance interval is **never created** for these users — not merely sped up. This matters because CSS alone cannot stop a JS-driven state change; the slide would still jump instantly every 3.5 seconds. Handling it in JS is the correct and commonly-missed solution.

## 10.3 Assessment

The animation strategy is **restrained and appropriate to the audience**. For users on cheap Android hardware over patchy data, the absence of scroll-triggered reveals and a JS animation library is a feature, not a gap: no layout thrash, no main-thread contention, no additional bundle weight.

Every animation is on `transform`, `opacity`, `box-shadow`, or `color` — all compositor-friendly properties. No animation touches `width`, `height`, `top`, or `margin`, so none can trigger layout reflow.

**The one genuinely problematic animation is #10**, the pulsing red dot on `/watch` and `/give` — not for performance reasons, but because it communicates the opposite of the truth.

# 13. PERFORMANCE

## 13.1 Image optimisation

**The single most important performance dimension for this site**, given the 14.7 MB of source imagery and the low-bandwidth audience.

**Measured delivery** (verified against a running server, `w=1920&q=75`, WebP):

| Source | Source size | Delivered | Reduction |
|---|---|---|---|
| `HeroImage3-clean.png` | 1,664 KB | **47.3 KB** | 97.2% |
| `BishopHillary.png` | 1,865 KB | **110.2 KB** | 94.1% |
| `HeroImage2.jpg` (previous hero) | 148 KB | 102.2 KB | 31% |

`next/image` is doing exactly what it should — the oversized PNGs are a **repository-weight problem, not a runtime problem.**

**What is correct:**
- Every image on the site goes through `next/image`; there is not a single raw `<img>` or CSS `background-image` on a photograph
- `sizes` is accurate on every responsive image (`100vw` for the hero, per-tile values in the glimpse grid, `24rem`/`36rem` for fixed-width slots)
- Static imports supply intrinsic dimensions → **no cumulative layout shift from images**
- `placeholder="blur"` on all statically-imported images

**What is not:**
- ~8 MB of orphaned images committed to the repository
- Source assets are PNGs of photographs (`BishopHillary.png` at 1.9 MB, `Bishop-Hillary.png` at 3.0 MB) where JPEG/WebP would be an order of magnitude smaller at source
- Both hero and pastor images are PNG — the format is doing nothing for them

## 13.2 Lazy loading

- `priority` is set on **exactly one image** — the hero. Correct: it is the LCP element.
- Every other image inherits `next/image`'s default `loading="lazy"`.
- The `/visit` Google Map iframe carries `loading="lazy"` and `referrerPolicy="no-referrer-when-downgrade"`.
- `YouTubeFacade` implements the facade pattern to defer a ~1 MB YouTube iframe until user intent — **parked, awaiting the deferred `/watch` build** (§8a).

## 13.3 Font loading

Two variable fonts, self-hosted at build time, `display: swap`, `latin` subset only. No runtime request to `fonts.googleapis.com`, so no third-party DNS/TLS round trip on first paint.

**Cost:** two families rather than one. **Benefit:** a distinctive serif/sans pairing that carries the brand. Reasonable trade-off, correctly implemented.

## 13.4 Bundle size

Exceptionally lean:

- **Three runtime dependencies total**: `next`, `react`, `react-dom`
- **No UI library**, no icon library, no animation library, no date library, no utility library
- **22 icons are inline SVG** — tree-shakeable, zero package weight
- **Two client components** ship interactivity; a third (`YouTubeFacade`) is parked for the deferred `/watch` build and, being unimported, is absent from the bundle entirely
- All six routes prerender to static HTML

This is close to a best-case bundle profile for a content site.

## 13.5 Animations

All animations are on `transform`, `opacity`, `box-shadow`, or `color` — compositor-friendly properties that never trigger layout reflow. No animation library. No scroll listeners, no `IntersectionObserver`, no `requestAnimationFrame` loops. The only recurring JS timer is the carousel's 3.5s interval, which is not created at all under reduced-motion.

## 13.6 Potential bottlenecks

| Bottleneck | Assessment |
|---|---|
| **Full-viewport hero image** | `min-h-[calc(100svh-4rem)]` with `sizes="100vw"` means the largest breakpoint image is fetched on desktop. Mitigated by `priority` and 47 KB WebP output, but it remains the LCP-critical resource. |
| **Google Maps iframe** | Third-party, on the keystone conversion page. Lazy-loaded, so it should not block, but it is the only third-party runtime resource on the site. |
| **Carousel `setInterval`** | Runs indefinitely while the homepage is open. Negligible, and correctly suppressed for reduced-motion users. |
| **No analytics** | Not a performance cost — but it means **there is currently no way to measure any of this in the field.** No Core Web Vitals data, no conversion tracking, no error reporting. |
| **Repository weight** | 14.7 MB of images, ~8 MB orphaned. Affects clone/CI time, not runtime. |

## 13.7 A note on the development environment

During this audit the Turbopack **persistent dev cache** (`.next/dev/cache/turbopack`) was observed to become corrupted, producing repeated `FATAL: An unexpected Turbopack error occurred` panics with the misleading cause `"Next.js package not found"` — while page requests continued returning 200. The dependency tree was verified intact; the fix was deleting `.next`.

This is a **development-environment issue only** and does not affect production builds, but it is worth knowing: because Turbopack's cache survives dev-server restarts, "restart the server" does not clear it — deleting `.next` does.

# 14. CURRENT STRENGTHS

## 14.1 Strategic clarity

1. **A single, documented, ruthlessly-executed objective.** "Compel a first-time physical visit" is stated in `HANDOFF.md` and visible in every file. Most church websites try to serve six audiences and convert none; this one picks a target and commits.
2. **The funnel is enforced in code, not convention.** `PLAN_VISIT_HREF` is a single exported constant imported by 8 components. The destination cannot drift.
3. **The livestream-subordination rule is honoured visually and semantically** — below a divider, smaller type, lower opacity, no button treatment. A rule most teams would state and then quietly violate.
4. **WhatsApp-first is a correct, market-aware decision**, executed consistently: 12 deep links, each with a context-specific pre-filled message.
5. **`/visit` deliberately excluded from the nav** in favour of a high-contrast button — a considered conversion bet, documented in code comments.

## 14.2 Content architecture

6. **A genuine single source of truth.** Every real-world fact lives in one 392-line file. Change the phone number once and it updates the footer, `/visit`, and the JSON-LD simultaneously.
7. **Placeholders are self-documenting.** `[A genuine, friendly photo of the pastor]` tells you exactly what to supply. The `PhotoPlaceholder` component renders the label on the page. Nothing is silently blank or lorem-ipsum.
8. **Content reuse without duplication** — the same `departments` array renders as recruitment cards on Home and structural rows on About.
9. **TypeScript types on all content shapes** (`ChurchEvent`, `Testimonial`, `Department`, `Leader`, `Belief`) with `satisfies` for compile-time validation.

## 14.3 Technical execution

10. **Excellent Server/Client boundary.** Two client components on the entire site. Everything else is zero-JS static HTML.
11. **Zero unnecessary dependencies** — `next`, `react`, `react-dom`, and nothing else at runtime.
12. **Two deliberate image strategies**, correctly chosen per use case: crop-to-fill for backgrounds, natural-ratio for flyers whose baked-in text cropping would destroy.
13. **Static image imports everywhere** → build-time dimensions, blur-up, and a *build failure* rather than a silent broken image on a typo.
14. **Genuine two-state components** — `NextEvent` switches on data alone; publishing an event is a content edit, never a code change.
15. **Name-keyed rather than index-keyed image maps** for departments and events, so reordering content cannot mis-assign photos.
16. **Per-image crop correction** (`objectPosition`) as an optional field — a small, thoughtful affordance for awkward source photography.
17. **Property-scoped transitions**, never `transition-all`.
18. **All routes statically prerendered.**

## 14.4 Accessibility

19. **Skip link, correctly implemented and correctly targeted.**
20. **Two-layer reduced-motion handling** — global CSS *and* a JavaScript guard that prevents the carousel interval from ever being created. The JS half is commonly missed.
21. **Full ARIA carousel pattern** with per-slide labelling, `aria-current` dots, and pause-on-hover *and* pause-on-focus.
22. **44px touch targets enforced via `min-h-*`** rather than hoped for.
23. **Consistent 3px focus rings** with offset, globally and per-component.
24. **Semantic HTML throughout** — including a real `<dl>` for event metadata with `sr-only` labels.

## 14.5 Design system

25. **Token-driven** via Tailwind v4 `@theme` — colours, fonts, radii, and shadows are all single-source.
26. **Warm-tinted shadows** built on the text colour rather than neutral black — a small detail that keeps the whole surface coherent.
27. **A custom 22-icon SVG set** on a consistent grid and stroke weight, with zero library dependency.
28. **Documented anti-patterns** in `MASTER.md` — including the rejection of the generator's original proposals, with reasons.

## 14.6 Documentation

29. **Three layers of handover documentation already exist** — `HANDOFF.md` (human), `AGENTS.md` (AI agents), `design-system/` (design), plus `Church-architecture.pdf` (product spec).
30. **`HANDOFF.md` documents deferred work with design notes**, including a complete implementation plan for the Watch page that has not been built.
31. **Code comments explain *why*, not *what*** — e.g. the hero's scrim comment explains that the photo is already dark and therefore needs less help.

# 17. IMPROVEMENT OPPORTUNITIES

Ordered by impact. Each entry states **why it matters**, not merely what to change.

## HIGH IMPACT

### H1 — Fix the `/contact` 404 and add `not-found.tsx`
**Why:** A broken link in the footer appears on **every page of the site**, and it lands users on an unstyled error page with no way back. This is simultaneously the most visible defect and among the cheapest to fix. `HANDOFF.md` already documents the intended resolution (Contact is deliberately not a page), so repointing the link to `/visit` matches design intent.

### H2 — Replace all placeholder testimonial and leadership identities
**Why:** These two sections exist *solely* to build trust, and in their current state they do the opposite. An anonymous testimonial reads as fabricated; a leadership page showing `[Name]` and gradient panels tells a visitor the church could not produce three real people. Every other trust signal on the site is undermined by these two sections. Note that a real photograph of the Bishop already exists in the repo and simply is not wired to the About page.

### H3 — Add analytics and conversion tracking
**Why:** The entire site is architected around one measurable objective, and **that objective is currently unmeasurable**. There is no way to know whether the funnel converts, which CTA performs, whether anyone reaches `/visit`, or how many WhatsApp conversations originate from the site. Every optimisation decision after this point is guesswork without it. WhatsApp click tracking is the single most valuable event to capture.

### H4 — Resolve the stale/past "upcoming" events
**Why:** Three of four events listed under "Upcoming" are dated July 2026 and are already in the past. The content file's own comment names this exact failure: *"a stale event at the top is a credibility killer."* A visitor who sees a past event advertised as upcoming reasonably concludes the church does not maintain its own website — and by extension, may not be well-run.

### H5 — Render the authored `/visit` content
**Why:** Four complete Q&As answering *"What's the worship like? / What happens when I arrive? / Will I be singled out? / What should I wear?"*, plus kids' safeguarding detail and practical logistics, are already written and sitting in `church.ts` **unrendered**. This is the precise anxiety-reducing material the entire funnel exists to deliver, on the exact page it was written for. It is the highest-value content in the codebase and it costs no new writing.

### H6 — Fix the `ReadyToJoin` run-on sentence
**Why:** A grammatical defect currently renders on **three pages** in the closing conversion block: *"…making many mighty through the Word and Prayer Come and see…"*. It appears at the highest-attention moment on each page.

### H7 — Add a prayer request path
**Why:** For a Pentecostal church whose own beliefs section states *"We're a praying church… we expect Him to answer"*, having no prayer entry point is a significant mismatch between stated identity and delivered function. A dedicated WhatsApp deep link with an appropriate pre-filled message would cost one line of code and serve a genuine, unserved need.

### H8 — Update the design-system documentation to match the shipped code
**Why:** `MASTER.md` documents the brand as purple `#6D28D9`; the site ships blue `#4B70C2`. Any incoming designer or developer reading the design system as their source of truth **will build the wrong colour.** The same file documents a dark-mode palette that was never implemented, and `pages/home.md` describes a homepage section order that no longer exists. Stale documentation is worse than no documentation because it is trusted.

## MEDIUM IMPACT

### M1 — Add machine-readable event dates and automatic expiry
**Why:** Currently `date` is a display string, so nothing can compare an event to today. Adding an ISO field and filtering on it converts H4 from a recurring manual chore into a solved problem. The two-state `NextEvent` component already exists to receive it.

### M2 — Complete `/watch`
**Why:** It occupies a primary nav slot, is linked from every page's closing CTA, and the homepage actively advertises *"Live this Sunday from 7:00 AM"*. The full implementation design already exists in `HANDOFF.md` §8a, and `YouTubeFacade` is already built and parked for it. This is specified, partially-built work sitting idle behind a placeholder.

### M3 — Complete `/give`, or add offline giving details
**Why:** "Give online" holds prime secondary-CTA real estate in the hero, and there is currently **no way for a motivated donor to give at all** — not even bank details. If the payment integration is not imminent, publishing account details is a near-zero-cost interim that unblocks real revenue.

### M4 — Fix the mobile menu's focus management
**Why:** No focus trap and no Escape-key close are the two most common mobile-menu accessibility failures, and both are present. Keyboard and screen-reader users can tab out of an open menu into content they cannot see.

### M5 — Fix the carousel tab order
**Why:** Slides marked `aria-hidden="true"` still contain focusable content, which is a direct `aria-hidden` violation — a keyboard user can land on an invisible slide with no visual indication of where their focus went.

### M6 — Add SEO fundamentals
**Why:** `sitemap.ts`, `robots.ts`, `metadataBase`, an OG image, and a homepage-specific meta description are all standard and cheap. Critically, **`sameAs` in the JSON-LD currently points at placeholder social accounts**, which actively feeds incorrect entity data to search engines — worse than omitting the field.

### M7 — Adopt `Button` across the ~10 hand-rolled CTAs
**Why:** The same 15-class string is duplicated roughly ten times. Any future change to CTA styling — including fixing the AAA contrast shortfall — currently requires ten synchronised edits with no compiler assistance. `HANDOFF.md` acknowledges some were hand-rolled for dark-hero treatments; those justify a variant, not duplication.

### M8 — Give `PastorWelcome` a proper heading
**Why:** It is the only homepage section missing from the document outline, so screen-reader users navigating by heading skip the Bishop's welcome entirely. Adopting the `Section` component fixes this and removes bespoke markup.

### M9 — Re-check contrast against the stated AAA target
**Why:** The purple→blue change reduced white-on-primary from ~7.1:1 to **4.73:1** — still AA-compliant, but a ~30% regression away from the project's own documented AAA goal. This appears to have been an unexamined side-effect of a brand decision, and the team should decide consciously whether AA is now the target.

## LOW IMPACT

### L1 — Delete orphaned images and dead code
**Why:** ~8 MB of unreferenced images, one dead component, six dead icons, and eight dead content fields. No runtime cost, but every one of them is a false signal to the next developer about what is actually in use.

### L2 — Rename `--color-purple-soft`
**Why:** A token named "purple" holding a blue value across 8 usages is a small, persistent source of confusion.

### L3 — Extract a shared `PageHero`

# 19. FINAL SUMMARY

## 19.1 Current maturity

**This is a well-architected, professionally-built shell that is roughly 60% populated with real content.**

The distinction matters enormously for anyone taking this over. The *engineering* is close to production quality — the component architecture is clean, the Server/Client boundary is excellent, accessibility was designed in rather than retrofitted, and the funnel strategy is enforced in code rather than left to convention. Someone thought carefully about this codebase, and left three layers of documentation explaining why.

The *content* is not ready. Fourteen photo placeholders remain, all four testimonials are anonymous, all three leadership profiles are placeholders, three of four "upcoming" events are dated in the past, two of the four navigation destinations are "Coming soon" pages, and bracket placeholders render visibly in live copy.

The gap between these two states is the defining characteristic of the project. **It is not half-built; it is fully built and half-filled.**

There is also a documentation-drift problem worth naming plainly: the design system, the per-page specs, and parts of `HANDOFF.md` describe an earlier version of this site. The brand colour changed from purple to blue in code without the design system following. An incoming team that trusts `MASTER.md` will build the wrong thing.

## 19.2 Biggest strengths

1. **Strategic discipline that survives contact with the code.** One objective, enforced by one constant, imported by eight components. Most projects state a strategy in a document and abandon it in implementation; this one did not.
2. **A genuine single source of truth.** 392 lines in one file drive every page, the footer, and the structured data simultaneously. Changing the phone number is one edit.
3. **Accessibility done properly, not performatively.** The skip link, the two-layer reduced-motion handling, the full ARIA carousel pattern, and enforced 44px touch targets represent real, deliberate work.
4. **An exceptional Server/Client boundary.** Two client components on the entire site; everything else is zero-JS static HTML — precisely correct for the low-bandwidth audience it targets.
5. **Honest, self-documenting placeholders.** `PhotoPlaceholder` renders a label describing exactly what photo belongs there. Nothing is silently missing or faked.
6. **Zero dependency bloat.** Three runtime packages. No UI library, no icon library, no animation library.
7. **Thoughtful image handling** — two deliberate strategies, static imports, per-image crop correction, and build-time failure on typos.

## 19.3 Biggest risks

| Risk | Severity | Explanation |
|---|---|---|
| **Trust collapse from placeholder content** | 🔴 **Critical** | Anonymous testimonials, placeholder leaders, and visible `[brackets]` actively damage credibility. The sections designed to build trust currently erode it. |
| **No measurement** | 🔴 **Critical** | The site is engineered around one measurable goal and has no analytics. Nobody can tell whether it works, and every future decision is guesswork. |
| **Stale events and a promised-but-absent livestream** | 🟠 High | Past events under "Upcoming" and a homepage advertising a non-existent stream both signal an unmaintained site. |
| **Documentation drift** | 🟠 High | The design system documents the wrong brand colour and a homepage layout that no longer exists. The next team will be actively misled. |
| **`/contact` 404 on every page** | 🟠 High | A visible broken link sitewide, landing on an unstyled dead end. |
| **Two nav destinations are placeholders** | 🟡 Medium | Half the primary navigation leads nowhere useful. |
| **Bus-factor on undocumented decisions** | 🟡 Medium | Several strategic choices (excluding `/visit` from nav, no forms, subordinating the livestream) are correct but unconventional. They are documented in `HANDOFF.md` — which is itself partially stale. |
| **Contrast regression against a stated AAA target** | 🟡 Medium | White-on-primary fell from ~7.1:1 to 4.73:1 as an unexamined side-effect of a brand change. |
| **No tests, no CI** | 🟡 Medium | Verification is entirely manual. One lint error currently blocks adding lint to a pipeline. |
